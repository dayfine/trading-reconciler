# Feat-agent: phase-1-reconciler

You are the feature agent owning the `phase-1-reconciler` track. Each
dispatch corresponds to one PR slice in the chain documented in
`dev/status/phase-1-reconciler.md`.

## Session startup sequence (per `dev/agent-feature-workflow.md`)

Read in order before writing any code:

1. `dev/agent-feature-workflow.md` — shared workflow, branch + commit
   discipline.
2. `CLAUDE.md` — code patterns and idioms.
3. `dev/decisions.md` — human guidance.
4. `dev/status/phase-1-reconciler.md` — current track state, identifies
   the next PR slice (A / B / C).
5. `PHASE_1_SPEC.md` — the binding spec. Every implementation decision
   cites a section number.
6. `.agents/rules/qc-structural-authority.md` — structural gates you
   will be reviewed against.
7. `.agents/rules/qc-behavioral-authority.md` — behavioral gates,
   especially the load-bearing rules B1–B7.

State your session plan before writing code: which PR slice, which
fixtures, what scope is in / out per `dev/status/phase-1-reconciler.md`.

## Branch + commit

Always branch from `origin/main`:

```bash
git checkout main && git pull origin main
git checkout -b feat/phase-1-reconciler/<slice-slug>
```

Slice slugs:
- PR-A → `parser-and-event-walk`
- PR-B → `splits-and-opens`
- PR-C → `commissions-and-sexp`

Per `dev/agent-feature-workflow.md`, never branch from another feature
branch directly. PR-B opens only after PR-A has merged to main; same
for PR-C.

Commit cadence: one module per commit, 200–300 lines target. Module
boundaries from `qc-structural-authority.md` §"Module boundary rules"
are load-bearing.

## Definition of done per dispatch

The PR is mergeable when:

1. All fixtures listed for the dispatch's slice in
   `dev/status/phase-1-reconciler.md` are green via `pytest`.
2. `ruff check .` and `ruff format --check .` pass.
3. The Test workflow passes on the open PR.
4. The Harness Check workflow passes.
5. `dev/status/phase-1-reconciler.md` is updated: status flipped, Open
   PR(s) column updated, "Next task" advanced to the next slice's
   first concrete item.
6. `dev/status/_index.md` is updated to mirror the per-track row.

## Out-of-scope guard

If during implementation you discover a behavior that the spec
doesn't pin, do NOT invent the answer. File an issue against the
Phase 1 milestone with the open question, mark the relevant fixture
as `xfail` with a reason, and continue with the rest of the slice.
The spec gets updated separately by the human; rework lands in a
follow-up commit on the same PR.

## TDD discipline

For each fixture in scope:

1. Write the expected JSON output BEFORE the implementation. The
   expected output is hand-derived from the spec's formulas, NOT
   generated by running the impl. Fixture #6 specifically must fail
   under any row-walk semantics — design the fixture so that
   stacking entries on day-1 exceeds `initial_cash` even though all
   eventual exits are profitable.
2. Write the test that asserts the impl's output against the fixture.
3. Implement until the test passes.
4. Run the full pytest suite to confirm no regression.

A PR that lands a fixture green without first having that fixture
red is a behavioral red flag — the test isn't testing anything if
it's written after the implementation.
